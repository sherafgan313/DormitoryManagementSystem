REQUIREMENT 1: Admin Profile Stored and Fetched from Database
--------------------------------------------------------------------------------

REQUIREMENT 3: Multiple Dormitories, Multiple Admins per Dormitory
--------------------------------------------------------------------------------
WHAT:
  System now supports multiple dormitories. Multiple admin accounts can manage
  the same dormitory. One user can only belong to one dormitory.

HOW:
  • New DB table: dormitories (dormitory_id, name, address, contact_email,
    contact_phone, max_capacity).
  • admin_profiles links each ADMIN user to exactly one dormitory (UNIQUE on
    user_id ensures one-dorm-per-admin).
  • users.dormitory_id enforces one-dormitory-per-user (for students, set on
    acceptance; for admins, set at account creation).
  • Seeder creates 2 dormitories:
    – "Sunrise Dormitory" (admin@dms.com / admin123)
    – "Moonlight Dormitory" (admin2@dms.com / admin123)
  • dormitory_id is included in the JWT payload so every request carries
    context without extra DB queries.

FILES CHANGED:
  Documentation/dorm_management.sql — new dormitories table; FK on users
  server.js — seedDemoData() with 2 dorms; JWT includes dormitory_id

REQUIREMENT 5: Room Counts, Room Assignment on Acceptance, Room Status Updates
--------------------------------------------------------------------------------
WHAT:
  Room inventory (total/occupied/vacant/maintenance) is now tracked in the DB.
  When an admin accepts an application, they must select a vacant room. The
  room status, resident link, and student profile are all updated automatically.

HOW:
  • New DB table: rooms (room_id, dormitory_id, room_number, floor, type,
    status ENUM('occupied','vacant','maintenance'), resident_id).
  • GET /api/stats returns totalRooms, occupiedRooms, vacantRooms,
    maintenanceRooms (all derived live from the rooms table).
  • GET /api/rooms — all rooms for admin's dorm with resident_name JOIN.
  • GET /api/rooms/vacant — only vacant rooms (for the acceptance dropdown).
  • PATCH /api/applications/:id/status — when status=ACCEPTED:
    1. Requires room_id in request body.
    2. Runs a DB transaction:
       a. UPDATE rooms SET status='occupied', resident_id=userId WHERE vacant.
       b. UPDATE users SET dormitory_id = admin's dorm.
       c. UPSERT student_profiles (dormitory_id, room_id, application_status).
       d. UPDATE dorm_applications (status, dormitory_id, assigned_room_id).
    3. Rolls back if room is not vacant (prevents double-assignment).
  • Admin dashboard Residents section has a two-step Accept flow:
    1. Click "Accept" → loads vacant rooms, shows dropdown in that table row.
    2. Select room → click "Confirm" → sends PATCH with room_id.
    3. On success, reloads applications, stats, and rooms.

FILES CHANGED:
  Documentation/dorm_management.sql — new rooms table
  server.js — GET /api/rooms, GET /api/rooms/vacant, PATCH /api/applications/:id/status (transaction)
  src/app/services/api.service.ts — getRooms(), getVacantRooms(), updateApplicationStatus() with room_id
  src/app/pages/dashboard/dashboard.ts — startAcceptApplication(), confirmAcceptApplication(), rejectApplication(), loadRooms()

REQUIREMENT 7: State Management Fix — Auto-Load on Navigation
--------------------------------------------------------------------------------
WHAT:
  Data now loads automatically. Previously, some sections only loaded data
  after specific button clicks. Now all sections preload on init and reload
  on every navigation.

HOW:
  Admin Dashboard (DashboardComponent):
  • ngOnInit() now calls: loadAdminStats(), loadRooms(), loadActivity(),
    loadApplications(), loadComplaints(), loadPayments(), loadReports(),
    loadAdminProfile() — all triggered immediately on component mount.
  • setActive(id) always triggers a reload for the relevant section:
    'dashboard' → loadAdminStats() + loadActivity()
    'rooms'     → loadRooms()
    'residents' → loadApplications()
    'payments'  → loadPayments()
    'requests'  → loadComplaints()
    'reports'   → loadReports()
    'settings'  → loadAdminProfile()
  • Mutations (accept/reject, status update, record payment, generate report)
    trigger reload of the relevant list after success.

  Student Dashboard (StudentDashboardComponent):
  • ngOnInit() now calls: loadProfile(), loadMyContract(), loadComplaints(),
    loadApplications(), loadPayments() — all triggered on mount.
  • setActive(id) always triggers reload for the target section.

FILES CHANGED:
  src/app/pages/dashboard/dashboard.ts — ngOnInit and setActive updated
  src/app/pages/student-dashboard/student-dashboard.ts — ngOnInit and setActive updated
